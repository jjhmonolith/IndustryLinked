# [본선 · 3차시] 피드백 분석과 도구 개선 계획 수립 멘토링 — 의견을 어떻게 반영할까 — 상세 진행안

> 시간: 14:00–17:00 (3h) / 담당: 팀모노리스 멘토(배영빈·류호선·이동연·이창환·김예진) + 업스테이지 멘토(이준엽·전영훈·최선웅·김남혁·조은비) / 분반: 5분반(40명/반), 반별 전담 멘토

## 0. 이 차시 한눈에
- **목표(1줄)**: 오전에 받은 동료 피드백 중 '오늘 안에 실현 가능하고 효과 큰' 개선을 선별해, 개발 환경에서 실제로 도구를 개선하고 전·후 차이를 기록한다.
- **산출물**: ① 적용/보류로 분류된 피드백 선별 목록(보류 사유 포함) ② 우선순위·작업 단위·예상 효과 개선 계획표 ③ 개선 전·후 동작 차이 기록 + 실제 개선 반영된 도구 버전 ④ 최종 발표 강조 개선점 1~2개.
- **앞 차시 연결**: 2차시(수업 시연·동료 피드백)에서 사용자 관점으로 받은 4항목(완성도·창의성·교육적 가치·활용방안 구체성) 피드백을 재료로 이어받는다.
- **다음 차시 연결**: 4차시(17:00–19:00) 최종 발표에서 오늘 개선한 도구를 3분 발표하고 동료 루브릭·심사위원 종합 평가를 받는다.

## 1. 사전 준비 (강사 체크리스트)
- [ ] 반별 전담 멘토 배정 확정 — 팀모노리스 멘토 1명 + 업스테이지 멘토 1명이 한 반(40명)을 분담, 순회 동선 사전 합의
- [ ] 2차시에서 취합한 4항목별 동료 피드백 모음이 참가자별로 코들에 준비됐는지 확인
- [ ] 도구 개선 계획 양식(우선순위·작업 단위·예상 효과 열) 코들 배포, 예시 1행 채워진 샘플 준비
- [ ] 개발 환경(Colab/API 키) 사본 재발급 링크, Solar LLM API 공용 예비 키, Document Parse + Information Extract 접근 확인
- [ ] 반별 대기열 관리 방법(멘토링 신청 보드/순번) 합의 — 대기 발생 시 문서화 병행 안내 준비
- [ ] 개선 전·후 비교용 '동일 입력' 기록 템플릿(입력 / 개선 전 응답 / 개선 후 응답) 준비
- [ ] 심화 미션 1줄 준비 — "안전장치 하나 더", "다른 학년용 변형" 등 일찍 끝난 팀용

## 3. 강사 스크립트 (핵심 순간 대본)

### 오프닝 (전담 멘토)
[강사 멘트] "선생님들, 오전에 동료분들께 정말 많은 피드백을 받으셨죠. 그거 다 읽어보시면 마음이 두 갈래로 갈릴 겁니다. '아 이거 맞다, 고쳐야겠다' 하는 것도 있고, '이걸 다 어떻게 하지…' 싶은 부담도 있을 거예요."
[강사 멘트] "그래서 오늘 오후의 첫 원칙을 딱 하나만 기억해 주세요. **모든 피드백을 반영하지 않습니다.** 효과가 크고, 오늘 세 시간 안에 실제로 손볼 수 있는 것 — 그것부터 골라서 확실하게 바꿉니다. 열 개를 어설프게 손대는 것보다, 하나를 제대로 바꾸는 게 오늘의 성공입니다."

### 반별 멘토 배정
[진행] 반별 배정표를 띄우고 담당 멘토(팀모노리스 1인 + 업스테이지 1인)를 소개한다.
[강사 멘트] "이 반은 저희 두 사람이 끝까지 함께합니다. 개발 쪽으로 막히는 건 이쪽에, AI 응답 품질이나 자료 처리 쪽은 저쪽에 편하게 물어보세요. 다만 한 가지 — 저희가 대신 코드를 짜 드리진 않습니다. 막힌 지점을 함께 들여다보고 힌트를 드릴게요. 손은 선생님이 움직이셔야 오늘이 남습니다."

### [실습 지시] 적용/보류 선별 (블록 2)
[실습] 코들 선별 목록을 엽니다. 오전 피드백을 한 항목씩 읽으며 '적용 / 보류' 둘 중 하나로 표시하세요. 판단 기준은 딱 두 가지 — ① 오늘 안에 실제로 손볼 수 있는가 ② 학생·수업에 효과가 큰가.
[강사 멘트] "보류로 넘긴 건 버리는 게 아닙니다. '왜 지금은 아닌지' 한 줄만 남겨 주세요. '시간이 더 필요해서', '데이터가 없어서' — 이 메모가 나중에 학교에 돌아가서 다시 손볼 때 지도가 됩니다."
[진행] 순회하며 모든 항목을 '적용'으로 표시한 교사에게: "이 중에 오늘 세 시간으로 진짜 다 되나요? 딱 두 개만 남긴다면 뭘 남기시겠어요?"

### [실습 지시] 개선 계획 수립 (블록 3)
[실습] 적용으로 고른 항목을 개선 계획표에 옮깁니다. 각 항목마다 세 칸을 채웁니다 — **우선순위 / 작업 단위 / 예상 효과**. 특히 '작업 단위'는 '30분 안에 끝날 만한 크기'로 쪼개세요.
[강사 멘트] "'답변을 더 정확하게'는 계획이 아니라 소원입니다. '주제 벗어난 질문에 안내 문구를 띄운다', '프롬프트에 학년 정보를 한 줄 추가한다' — 이렇게 손이 닿는 크기로 잘라야 오늘 안에 끝납니다."
(예상 효과 칸에는 반드시 '어떻게 확인할지'까지 — 같은 질문을 개선 전·후에 넣어 응답을 비교하는 방식을 안내)

### [실습 지시] 멘토링 고도화 (블록 4)
[강사 멘트] "본격적으로 개선 들어가기 전에, 딱 한 가지만 먼저 하세요. 개선하려는 그 기능에 **평소 입력을 하나 넣고, 지금의 응답을 캡처해 두는 겁니다.** 이게 '개선 전' 사진이에요. 이걸 안 찍어두면, 이따가 좋아졌는지 나빠졌는지 증명할 수가 없습니다."
[진행] 멘토링은 신청 순 1:n으로 진행. 막힌 팀은 "지금 어디까지 됐고, 어디서 멈췄나요?"로 시작해 대신 만들지 않고 다음 한 걸음만 짚어준다.
(자료 기반 챗봇 팀이 응답 범위가 어긋나면 Document Parse 파싱 결과·Information Extract 추출 항목을 육안 검수부터 — 원문이 깨졌는지, 추출이 빠졌는지 순서로 확인)
[강사 멘트] "개선 한 번 하셨으면, 아까 그 똑같은 입력을 다시 넣어 보세요. 응답이 어떻게 달라졌는지 나란히 놓고 기록하시면, 그게 이따 발표에서 가장 강력한 한 장면이 됩니다."

### [전환] 정리·발표 준비 (블록 5)
[강사 멘트] "세 시간 동안 여러 군데 손보셨을 텐데, 이따 발표에서 다 말할 시간은 없어요. 오늘 개선 중에 '이건 진짜 잘 됐다' 싶은 딱 한두 개만 고르세요. 개선 전·후 비교 기록이 있으면 그걸 그대로 보여주시면 됩니다."

### 마무리 (전담 멘토)
[강사 멘트] "오늘 여러분은 남의 의견에 휘둘리지 않고, 골라서, 실제로 바꾸는 걸 해내셨습니다. 개선 계획표랑 전·후 기록 코들에 올려 주시고요. 잠깐 숨 고르신 뒤, 다섯 시부터 그 개선한 도구를 동료분들 앞에서 발표하고 마지막 평가를 받습니다."

## 4. 강의 가이드라인 (이 차시 특화)
- **강조점**: **"모든 피드백 반영 금지 — 효과 크고 오늘 가능한 것부터."** 이 한 문장이 3시간 전체의 축. 개선은 반드시 개발 환경에서 실제 동작으로 확인하고, 동일 입력 전·후 비교로 변화를 눈에 보이게 남긴다.
- **피해야 할 것**: 멘토가 대신 코드 작성 / 참가자가 개선 범위를 무한정 늘리도록 방치 / 계획 없이 곧장 코드부터 만지기 / 특정 도구·모델 자랑.
- **톤**: 심판이 아니라 코치. "그건 안 됩니다"보다 "그럼 이 부분만 먼저 해볼까요". 코딩 저경험 교사가 위축되지 않게, 성공 기준을 '작동하는 개선 하나'로 낮춰 반복 안내.
- **시간 관리**: 블록 4(멘토링 80분)가 실습 심장부 — 여기 시간을 지킨다. 지연 시 블록 2·3의 부가 설명을 먼저 줄이고, 정리(블록 5)의 발표 준비만 확보. 각 블록 종료 2분 전 '전환 신호'로 리듬 유지.

| AI 응답 품질 개선이 눈에 안 보임 | 동일 입력으로 개선 전·후 응답을 나란히 기록해 변화 가시화 |
