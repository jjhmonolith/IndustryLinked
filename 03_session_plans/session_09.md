# [9차시 / 50분] 트랙 기술 1

**주관**: 공동 (기술 = 업스테이지 / 적용 = 팀모노리스) / **분반**: 트랙별 분반

## 학습 목표 (트랙 공통)

1. 트랙 핵심 기술의 작동 원리를 한 그림으로 그릴 수 있다.
2. 짓다에서 그 기술을 "어떻게 시키는지" 프롬프트 패턴 1개를 손에 익힌다.
3. 자기 MVP v0에 이 기술을 어디에 어떻게 끼울지 결정한다.

---

## 트랙 A — 자동 채점 로직 + 안전한 LLM 평가

### 9차시 A 구성

| 시간 | 내용 |
|------|------|
| 0-5분 | 도입 — "자동 채점이 어떻게 가능한가?" |
| 5-15분 | **자동 채점 2가지 방식**: ① 입출력 매칭(IO) ② 단위 테스트(unit test). 사례·장단점 |
| 15-25분 | **AI 테스트케이스 생성** 패턴 — 강사가 짓다에서 시연 ("이 문제에 대한 테스트케이스 5개 만들어줘") |
| 25-42분 | **실습**: 자기 문제 1개에 대해 (a) 정답·오답 코드 → 채점 결과 / (b) LLM이 테스트케이스 생성하도록 호출 |
| 42-50분 | 팀별 공유 + 한계 토의 ("LLM이 만든 테스트케이스는 믿을 만한가?") |

### 핵심 패턴

```
[학생 코드]
   ↓
[1] 테스트케이스(여러 입력) 실행
   ↓
[2] 기대 출력과 비교
   ↓
[3] 통과/실패 + 어디서 실패했나 표시
```

### 짓다 프롬프트 패턴 예시

```
당신은 파이썬 자동 채점 시스템입니다.
다음 문제에 대해, 학생 코드가 정답인지 판단하기 위한 테스트케이스 5개를
JSON 배열로 만드세요. 각 항목은 {"input": ..., "expected_output": ...} 형식.

[문제]
{문제 텍스트}

[정답 예시]
{정답 코드}
```

### 트랙 A 한계와 솔직한 메시지

- 짓다 환경에서 학생 코드를 실제 실행하기 어려울 수 있음. **검증 필요 항목** (사전에 짓다 측 확인).
- 대안: (a) 문자열 매칭으로 단순 검증, (b) Solar에게 "이 코드를 실행하면 어떤 결과가 나올까" 시뮬레이션, (c) Pyodide 임베드. 9차시는 그중 가장 단순한 방식 채택.

## 트랙 B — RAG 구축 5단계

### 9차시 B 구성

| 시간 | 내용 |
|------|------|
| 0-5분 | 도입 — "어제 챗봇은 환각이 있었다. 왜? 어떻게 막나?" |
| 5-15분 | **RAG 5단계** 그림 — 자료 → 청크 → 임베딩 → 검색 → 답변. 각 단계 30초 |
| 15-25분 | **짓다에서 RAG 구현 패턴** 시연 — 업스테이지 임베딩 API + 단순 in-memory 검색 |
| 25-42분 | **실습**: 자기 단원 발췌문 3-5개를 넣고, 학생 질문에 발췌문 기반으로 답하는 챗봇 |
| 42-50분 | 팀별 공유 + 한계 토의 ("자료를 더 잘 자르려면? 검색이 빗나갈 때는?") |

### 핵심 패턴 그림

```
[교사가 자료 업로드]
   ↓
[1] 자료를 작은 조각(청크)으로 자르기
   ↓
[2] 각 조각을 벡터(임베딩)로 변환 → 저장
   ↓
[학생 질문 들어옴]
   ↓
[3] 질문도 벡터로 변환
[4] 가장 가까운 조각 3개 찾기
   ↓
[5] LLM에게 "이 조각들 + 질문" 던지면서 답변 생성
   ↓
[학생에게 답 + 출처 표시]
```

### 짓다 프롬프트 패턴 예시

```
당신은 [학년] [과목] 학습 도우미입니다.

다음 자료의 범위 안에서만 답변하세요:
---
{retrieved_chunks}
---

규칙:
1. 자료에 없는 내용은 "교재에서 확인 어렵다"고 답하세요.
2. 답변 끝에 어느 자료를 참고했는지 표시하세요.
3. 답을 직접 주지 말고, 학생이 자료에서 찾을 수 있도록 질문해주세요.

학생 질문: {user_question}
```

### 트랙 B 한계와 솔직한 메시지

- 짓다에서 벡터 검색을 어디까지 지원하는지 확인 필요. **검증 필요 항목**.
- 대안: in-memory 단순 keyword 매칭 + 임베딩 유사도. 정교한 벡터DB는 본 연수 범위 외.
- 한 단원 분량(예: 5-10페이지)까진 단순한 구현으로도 충분.

## 강사 핵심 메시지 (공통)

- "오늘은 *이론*이 아니라 *짓다에게 뭐라고 시키는지*가 핵심. 5분짜리 이론, 40분짜리 실습."
- "동작하는 한 줄 호출이 안 동작하는 완벽한 이해보다 낫다."
- "한계도 솔직히. 짓다·Solar로 안 되는 부분은 안 된다고 말하자."

## 사전 준비물

- 트랙 A: 자동 채점 짓다 스타터 + 예시 문제 3개
- 트랙 B: RAG 짓다 스타터 + 예시 단원 발췌문 3개
- 멘토 4-5명 / 트랙

## 체크포인트

- 트랙 A: 자기 문제 1개에 대해 정답·오답 분리 결과를 짓다에서 확인
- 트랙 B: 발췌문 기반 답변과 "교재에 없음" 거절 모두 1회 이상 확인

## 흔한 실패 패턴과 대응

| 실패 | 대응 |
|------|------|
| RAG 이론 설명이 너무 길어짐 | 5단계 그림 1장으로 끝내고 즉시 짓다 진입 |
| 학생 코드 실행이 안 되어 채점 검증 막힘 | 시뮬레이션 / 문자열 매칭 폴백. 강사 시연 가능 |
| 검색이 엉뚱한 조각을 찾아옴 | "청크 크기를 조정하면 어떻게 바뀌나" 실험 과제로 |
