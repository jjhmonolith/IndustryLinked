# [9차시 / 50분] 트랙 기술 1

**주관**: 공동 (기술 = 업스테이지 / 적용 = 팀모노리스) / **분반**: **트랙별 분반 개시** (8차시 트랙 확정 결과 반영)

## 첫 트랙 분반 차시 — 운영 안내

- 본 차시부터 트랙별 분반 운영이 개시된다. 참여 교원은 트랙별로 다른 공간에 입실한다.
- 참여 교원은 7차시에서 제작한 옵션 A 또는 옵션 B 챗봇을 출발 자료로 본 차시에 진입한다.
- 7차시 옵션과 다른 트랙으로 진입하는 경우에도 1~6차시 학습이 공통 기반으로 활용된다.
- 트랙별 코들 교실 2개를 본 차시부터 분리 운영한다(보드·활동지·퀴즈 전체).

## 학습 목표 (트랙 공통)

1. 본 트랙의 핵심 기술 작동 원리를 도식화할 수 있다.
2. 짓다에서 본 기술을 호출하는 프롬프트 패턴 1건을 작성·실행한다.
3. 본인 도구에서 본 기술의 결합 위치를 결정한다.

---

## 트랙 A — 자동 채점 로직 + 안전한 LLM 평가

### 9차시 A 진행 흐름

| 시간 | 내용 |
|------|------|
| 0-5분 | 도입 — 자동 채점의 구현 방식 개관 |
| 5-15분 | 자동 채점 2가지 방식 — ① 입출력 매칭(I/O) ② 단위 테스트. 사례·장단점 비교 |
| 15-25분 | AI 테스트케이스 생성 패턴 시연 — "본 문제에 대한 테스트케이스 5건 생성 요청" |
| 25-42분 | 실습 — 본인 문제 1건에 대해 (a) 정답·오답 코드의 채점 결과 / (b) LLM 기반 테스트케이스 생성 |
| 42-50분 | 팀별 공유 및 한계 토의 — "LLM이 생성한 테스트케이스의 신뢰성" |

### 핵심 패턴 (도식)

```
[학생 코드]
   ↓
[1] 테스트케이스(다수 입력) 실행
   ↓
[2] 기대 출력과 비교
   ↓
[3] 통과/실패 및 실패 지점 표시
```

### 짓다 프롬프트 패턴 예시

```
당신은 파이썬 자동 채점 시스템입니다.
다음 문제에 대해, 학생 코드의 정답 여부를 판단하기 위한 테스트케이스 5건을
JSON 배열로 생성합니다. 각 항목은 {"input": ..., "expected_output": ...} 형식으로 작성합니다.

[문제]
{문제 텍스트}

[정답 예시]
{정답 코드}
```

### 트랙 A 기술 한계 (사전 안내)

- 짓다 환경의 학생 코드 실시간 실행 지원 범위 확인 필요 — **검증 항목**(짓다 측 사전 확인 요청).
- 대안: (a) 문자열 매칭 기반 검증, (b) Solar 기반 실행 결과 시뮬레이션, (c) Pyodide 임베드. 본 차시는 가장 단순한 방식을 채택한다.

## 트랙 B — RAG 구축 5단계

### 9차시 B 진행 흐름

| 시간 | 내용 |
|------|------|
| 0-5분 | 도입 — 7차시 챗봇의 환각 사례 회고 및 RAG 도입 필요성 |
| 5-15분 | RAG 5단계 도식 — 자료 → 청크 → 임베딩 → 검색 → 응답. 단계별 30초 |
| 15-25분 | 짓다에서 RAG 구현 패턴 시연 — 업스테이지 임베딩 API + 인메모리 검색 |
| 25-42분 | 실습 — 본인 단원 발췌문 3~5건 입력 후 학생 질문에 발췌문 기반 응답하는 챗봇 제작 |
| 42-50분 | 팀별 공유 및 한계 토의 — "자료 분할 방식 개선, 검색 정확도 향상 방안" |

### 핵심 패턴 (도식)

```
[교사가 자료 업로드]
   ↓
[1] 자료를 작은 조각(청크)으로 분할
   ↓
[2] 각 조각을 벡터(임베딩)로 변환·저장
   ↓
[학생 질문 입력]
   ↓
[3] 질문을 벡터로 변환
[4] 최유사 조각 3건 검색
   ↓
[5] LLM에 "검색된 조각 + 질문"을 입력하여 응답 생성
   ↓
[학생에게 응답 + 출처 표시]
```

### 짓다 프롬프트 패턴 예시

```
당신은 [학년] [과목] 학습 도우미입니다.

다음 자료의 범위 내에서만 응답합니다:
---
{retrieved_chunks}
---

규칙:
1. 자료에 없는 내용은 "교재에서 확인 어려움"으로 응답합니다.
2. 응답 끝에 참고 자료를 표시합니다.
3. 정답을 직접 제공하지 않고, 학생이 자료에서 찾도록 질문으로 응답합니다.

학생 질문: {user_question}
```

### 트랙 B 기술 한계 (사전 안내)

- 짓다의 벡터 검색 지원 범위 확인 필요 — **검증 항목**(짓다 측 사전 확인 요청).
- 대안: 인메모리 키워드 매칭 + 임베딩 유사도. 정교한 벡터DB는 본 연수 범위 외.
- 단원 1개 분량(5~10페이지)은 단순 구현으로 처리 가능하다.

## 강사 강조 사항 (공통)

- 본 차시는 이론보다 *짓다 활용 패턴*이 중심이다. 이론 5분, 실습 40분.
- 작동하는 1줄 호출이 작동하지 않는 완전한 이해보다 우선한다.
- 짓다·Solar의 한계는 있는 그대로 안내한다.

## 사전 준비물

- 트랙 A: 자동 채점 짓다 기본 템플릿 + 예시 문제 3건
- 트랙 B: RAG 짓다 기본 템플릿 + 예시 단원 발췌문 3건
- 멘토 4~5명 / 트랙

## 성취 기준

- 트랙 A: 본인 문제 1건에 대해 정답·오답 분리 결과를 짓다에서 확인
- 트랙 B: 발췌문 기반 응답과 "교재에 없음" 거절을 각 1회 이상 확인

## 주요 위험 요인과 대응 방안

| 위험 요인 | 대응 방안 |
|-----------|-----------|
| RAG 이론 설명 시간 초과 | 5단계 도식 1장으로 종료, 즉시 짓다 실습 진입 |
| 학생 코드 실행 미지원으로 채점 검증 중단 | 시뮬레이션 또는 문자열 매칭 대체. 강사 시연 활용 |
| 검색 결과 오분류 발생 | "청크 크기 조정에 따른 변화" 실험 과제로 전환 |

## 짓다 / 코들 사용 시점

- 짓다: 15~42분 — 본 실습
- 코들 활동지: 42~50분 — "본인 도구의 한계 1건 및 다음 결정" 정형 입력
